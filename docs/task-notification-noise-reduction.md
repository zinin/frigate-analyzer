# ТЗ: снижение шума в уведомлениях о повторном появлении объектов

Задача поставлена по итогам живого прогона `v0.9.1` на проде в ночь со 2 на 3 августа 2026.
Документ самодостаточен — контекст, обоснование и приёмка внутри.

**Ветка:** `feature/notification-noise-reduction` (отрезана от `master` = `553f988`).
Кроме этого файла в ветке ничего нет.

---

## 1. Контекст

**Проект:** Frigate Analyzer — анализ записей камер Frigate, YOLO-детекция, уведомления в Telegram.
**Стек:** Kotlin 2.4.10, Spring Boot 4.1.0, WebFlux, R2DBC/PostgreSQL, Coroutines, Java 25.

В `v0.9.1` появилась ветка решения `REAPPEARED`: сматченный по IoU трек, которого не было дольше
`NOTIFICATIONS_TRACK_REAPPEAR_GAP`, считается вернувшимся и порождает уведомление. Фикс закрывал
реальный баг — при длинном `NOTIFICATIONS_TRACK_TTL=PT12H` кадр насыщался, любая новая детекция
перекрывалась по IoU с каким-нибудь существующим треком, `newTracksCount` всегда был 0, решение
уходило в `ALL_REPEATED`, и **уведомления о проходе человека не приходили вовсе**.

Фикс работает — целевой сценарий на проде воспроизведён. Но вскрылся побочный эффект: шум.

### Что реально пришло за ночь 23:00–08:00

Прод-настройки на момент прогона: `TTL=PT12H`, `REAPPEAR_GAP=PT1H`, `CLEANUP_RETENTION=PT48H`,
`IOU_THRESHOLD=0.3`, `CONFIDENCE_FLOOR=0.3`, три камеры.

| | |
|---|---|
| `Decision: notify (reappeared)` | **9** |
| `Decision: notify:` (NEW_OBJECTS) | 12 |
| `Decision: suppress (all_repeated)` | 5156 |
| `Decision: suppress (out_of_schedule)` | 1558 |

Дедупликация в целом работает — на 21 уведомление приходится 5156 подавлений. Проблема
в структуре этих 9 реаппиров.

### Разбор 9 реаппиров по механизму

**Группа A — мерцание статики, 4 шт.** (время MSK)

| Время | Камера | Класс |
|---|---|---|
| 02:18 | cam2 | bicycle |
| 03:43 | cam1 | cow, cow |
| 06:11 | cam2 | bicycle |
| 06:46 | cam3 | car |

Объекты физически неподвижны. Ночью детектор их теряет, на рассвете находит снова — разрыв
превышает `PT1H`, и это читается как возвращение. Два реаппира велосипеда на cam2 разделены
3 ч 53 мин, то есть отсутствие перед вторым было **меньше 3 ч 53 мин**.

**Группа B — пачка от одного прохода, 4 шт.**

```
20:40:55 UTC  cam3  reappearedClasses=[person]
20:40:57 UTC  cam2  reappearedClasses=[person]
20:41:08 UTC  cam2  reappearedClasses=[person]
20:41:19 UTC  cam2  reappearedClasses=[person]
```

Четыре уведомления за 24 секунды об одном событии. **Это разные треки.** В кадре накоплено
~107 активных треков `person` вдоль дорожки; идущий человек последовательно матчится с ними
один за другим, каждый из этих треков не обновлялся часами — каждый даёт свой реаппир.
Соответствующие строки трекера:

```
ObjectTracker: cam=cam2 new=0 matched=3 reappeared=1 unobserved=0 stale=107
ObjectTracker: cam=cam2 new=0 matched=4 reappeared=1 unobserved=0 stale=107
ObjectTracker: cam=cam2 new=0 matched=1 reappeared=1 unobserved=0 stale=110
```

**Группа C — полезное, 1 шт.** Проверочный проход владельца в 23:02.

### Почему это не лечится настройками

`NOTIFICATIONS_TRACK_REAPPEAR_GAP` — штатный регулятор, в KDoc прямо написано «pick a value above
the observed detector flakiness gap for static objects, otherwise they re-notify». Поднятие порога
снимает часть группы A, но:

- на группу B не влияет вообще — там все треки не обновлялись часами и переходят любой порог;
- чтобы снять рассветные реаппиры, нужен порог ~`PT10H` (объект не виден с вечера до утра),
  а `reappearGap == ttl` по построению делает фичу no-op, так что это равносильно отключению;
- отсутствие длиной 8–9 часов у неподвижного велосипеда **неотличимо по времени** от «человек
  ушёл вечером, вернулся утром» — одним порогом эти случаи не разделить.

Поднимать `CONFIDENCE_FLOOR` для борьбы с мерцанием **нельзя** — эффект обратный: отсечённые
слабые ночные детекции удлиняют наблюдаемое отсутствие статики, и реаппиров становится больше.

Значит нужен код.

---

## 2. Что делать

Три независимых изменения. **Каждое по умолчанию no-op** — поведение из коробки не меняется,
включение только явной настройкой. Это принципиально: тот же приём уже применён к `reappearGap`
(его дефолт равен `ttl`, что делает фичу выключенной), и он позволяет катить релиз без сюрпризов
и откатывать правкой `.env` без отката образа.

Изменения можно делать в любом порядке, но задача 3 полезна первой — она даёт данные для подбора
порогов в задачах 1 и 2.

### Задача 1 — кулдаун на повторные уведомления

**Цель:** схлопнуть группу B. Пачка из 4 реаппиров за 24 секунды должна давать 1 уведомление
на камеру.

**Область применения:** только ветка `REAPPEARED`. Ветку `NEW_OBJECTS` не трогать — появление
действительно нового объекта не должно теряться из-за недавнего реаппира.

**Параметр:** `application.notifications.cooldown.reappear` ←
`NOTIFICATIONS_COOLDOWN_REAPPEAR`, тип `Duration`, **дефолт `PT0S` = выключено**.

**Где:** `NotificationDecisionServiceImpl.evaluate`, в ветке `delta.reappearedTracksCount > 0`,
`modules/service/.../impl/NotificationDecisionServiceImpl.kt:75`.

**Ключ:** `camId`. Не `camId + класс` — в пределах одного прохода классы совпадают, а составной
ключ усложняет обработку многоклассовых решений (`reappearedClasses=[cow, cow]`) без выигрыша.

**КРИТИЧНО — по какому времени считать.** Сравнивать `recording.recordTimestamp`, а НЕ
`Instant.now()`. Причина: очередь необработанных записей дренится newest-first, и при разборе
бэклога (после рестарта, после залипшего пайплайна) десятки записей за час обрабатываются за
секунды. Кулдаун по wall-clock схлопнул бы весь бэклог в одно уведомление, потеряв реальные
события. Из-за того же newest-first порядок `recordTimestamp` не монотонен, поэтому хранить надо
максимум из увиденных, а сравнение вести с ним.

**Состояние:** in-memory, `ConcurrentHashMap<String, Instant>`. Персистентность не нужна —
горизонт кулдауна минуты, потеря при рестарте безвредна. Время брать через инжектированный
`Clock` (бин в проекте есть, используется трекером и health-индикаторами) — там, где вообще
понадобится wall-clock; основная логика на `recordTimestamp`.

**Новая причина:** добавить `COOLDOWN` в `NotificationDecisionReason`
(`modules/model/.../dto/NotificationDecision.kt`).

**Логировать** на DEBUG, консистентно с остальными suppress-ветками: подавления — общий случай,
на INFO они утопят notify-строки. Формат в духе существующих:

```
Decision: suppress (cooldown): cam=cam2 sinceLast=PT24S recording=<uuid>
```

**Трекер обновлять в любом случае.** Кулдаун гасит только отправку. Порядок в `evaluate` уже
такой: `tracker.evaluate` вызывается на строке 47, до всех гейтов — не сломать это. Иначе окно
наблюдения перестанет штамповаться и подавленное уведомление превратится в ложный реаппир позже.

### Задача 2 — ограничение реаппиров по классам

**Цель:** снять группу A целиком.

**Параметр:** `application.notifications.tracker.reappear-classes` ←
`NOTIFICATIONS_TRACK_REAPPEAR_CLASSES`, список строк, **дефолт пустой = все классы** (no-op).
Формат как у существующего `DETECTION_FILTER_CLASSES` — через запятую.

**Семантика:** класс, не входящий в список, не попадает в `reappearedClasses`, то есть
не может породить уведомление о возвращении. На ветку `NEW_OBJECTS` не влияет никак — уведомления
о новых объектах любого класса продолжают приходить.

Это важно и должно быть отражено в документации: владелец прода **не хочет** сужать
`DETECTION_FILTER_CLASSES` (коровы, птицы, собаки ему нужны). Речь только о том, что «корова
вернулась» — не событие, а «новая корова» — событие.

**Где:** `ObjectTrackerServiceImpl`, место формирования `reappearedClasses` —
`modules/service/.../impl/ObjectTrackerServiceImpl.kt:213-221`. Фильтровать при добавлении,
чтобы `reappearedTracksCount` не рос и решение естественно уходило в `ALL_REPEATED`.

Сравнение имён классов — регистронезависимое, с `trim`; пустые элементы списка игнорировать.

### Задача 3 — логировать фактическую длительность отсутствия

**Цель:** сейчас порог `REAPPEAR_GAP` подбирается вслепую — фактическая длительность отсутствия
нигде не видна, и понять, какое значение отсечёт мерцание, но сохранит реальные возвращения,
невозможно.

**Где:** строка сводки трекера, `ObjectTrackerServiceImpl.kt:243-249`. Сейчас:

```
ObjectTracker: cam=cam2 new=0 matched=3 reappeared=1 unobserved=0 stale=107 (recording=<uuid>)
```

**Добавить:**
- `maxAbsence=<Duration>` — максимальное отсутствие среди **всех** сматченных треков этой записи,
  включая те, что порог не перешли. Именно это число показывает, где проходит граница и каким
  порогом её можно сдвинуть;
- разбивку по сработавшим реаппирам с классом и длительностью, например
  `reappeared=[person:PT3H12M, bicycle:PT7H4M]`.

Существующее условие логирования (`newCount > 0 || reappearedClasses.isNotEmpty() ||
unobservedAbsences > 0`) сохранить — строка не должна появляться на каждой записи.

Уровень остаётся DEBUG. На проде DEBUG для `ObjectTrackerServiceImpl` и
`NotificationDecisionServiceImpl` уже включён точечно через `docker/deploy/application-docker.yaml`,
так что дополнительной настройки не потребуется.

## 3. Требования к реализации

- **Валидация свойств.** `ObjectTrackerProperties.init` уже проверяет инварианты и роняет контейнер
  на биндинге при нарушении — держаться этого стиля. Для кулдауна: `>= PT0S` (ноль = выключено,
  отрицательное — ошибка). Есть готовый образец теста биндинга:
  `modules/core/src/test/kotlin/.../config/properties/ObjectTrackerPropertiesBindingTest.kt`.
- **Тесты обязательны.** Текущее состояние `master` — 726 тестов, 0 падений, 1 skipped. Отправные
  точки: `NotificationDecisionServiceImplTest`, `ObjectTrackerServiceImplTest`. Покрыть минимум:
  кулдаун выключен по умолчанию; кулдаун гасит второе уведомление и пропускает после истечения;
  кулдаун не влияет на `NEW_OBJECTS`; кулдаун считается по `recordTimestamp`, а не по wall-clock
  (обработка бэклога не схлопывается); пустой список классов = все классы; класс вне списка
  не даёт реаппир, но даёт `NEW_OBJECTS`.
- **Документация.** Обновить `.claude/rules/configuration.md` (новые переменные, раздел про
  подбор `REAPPEAR_GAP` под длинный TTL) и `docker/deploy/.env.example` — там уже есть
  tracker-блок, строки 73–83.
- **Никаких миграций БД.** Схема не меняется, состояние кулдауна in-memory.

## 6. Что НЕ делать

- **Не сужать `DETECTION_FILTER_CLASSES`** — владелец прода явно попросил не трогать, коровы,
  птицы и собаки в уведомлениях ему нужны.
- **Не менять порядок гейтов** в `NotificationDecisionServiceImpl.evaluate`. Текущий:
  `NO_DETECTIONS` → `tracker.evaluate` → `NO_VALID_DETECTIONS` → `GLOBAL_OFF` → `OUT_OF_SCHEDULE`
  → `NEW_OBJECTS` → `REAPPEARED` → `ALL_REPEATED`. Вызов трекера **до** гейтов сделан намеренно:
  окно наблюдения должно штамповаться даже когда уведомление подавлено расписанием.
- **Не трогать `WatchRecordsLoop.registerAllDirs`** — там своя известная проблема (обход всего
  дерева записей, 9 минут на старте), она вынесена в отдельную задачу и в эту ветку не входит.
- **Не «дочинивать» принятые компромиссы**, задокументированные в KDoc `ObjectTrackerServiceImpl`:
  порог обнаружения перерыва равен самому gap; остаточный drain-order-кейс в `markWatched`;
  одноразовый всплеск после долгого tracker-only сбоя.
